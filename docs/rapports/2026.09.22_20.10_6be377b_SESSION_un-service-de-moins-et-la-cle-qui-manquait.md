## Decisions

1. **Le dépôt recipe-manager est archivé, pas supprimé** — il garde `docs/CORPUS_WEB.md` et
   `scripts/measure_parse_url.py`, qui portent les mesures par site. Son README dit désormais
   où chaque fichier est parti. **Alternative rejetée** : suppression, qui emportait ces mesures.
2. **Le credential Gemini garde son ancien nom** (`recipe-manager-gemini-key`) : le fichier du
   credstore est chiffré avec ce `--name`, et le reposer exige la clé en clair. `images.py`
   accepte les deux noms, donc le renommage se fera sans changement de code.
   **Alternative rejetée** : bloquer le déploiement sur un renommage de secret.
3. **Les 10 `.md` restants du vault ne sont PAS supprimés** — `Cadre-mediterraneen.md`,
   `Inspirations.md`, `Intentions.md`, `Produits-à-évaluer.md` n'ont aucun équivalent mesuré en
   base. L'ADR 0031 disait « les 118 `.md` », mais 118 est un compte de fichiers, pas une preuve
   de duplication. **Alternative rejetée** : suivre le chiffre de l'ADR et supprimer à l'aveugle.
4. **La contrainte `food_key` vit dans la migration, pas dans `SCHEMA_SQL`** : `food` y est créée
   APRÈS `pantry_item`, donc une `REFERENCES` posée dans le `CREATE TABLE` échouerait sur une
   base neuve. Colonne nue dans le schéma, contrainte et index dans `MIGRATIONS_SQL`.
5. **Le backfill de `shopping_session.status` est idempotent par construction** : colonne ajoutée
   sans défaut, `UPDATE ... WHERE status IS NULL` → `ordered`, PUIS défaut `cart`. Au second
   passage l'`UPDATE` touche 0 ligne. **Alternative rejetée** : un `WHERE created_at < date`,
   qui aurait fait dépendre la migration d'une date écrite en dur.

## Problems

1. **L'unité systemd installée gardait `Requires=recipe-manager.service`**
   — **Symptôme** : rien. `systemctl is-active cooking-manager` disait `active`.
   — **Cause** : le fichier du dépôt était corrigé, celui de `/etc/systemd/system/` non ;
   `disable` ne retire pas une dépendance `Requires`. Au prochain reboot, systemd aurait
   rallumé recipe-manager ou fait échouer CM2. — **Solution** : `cp` du fichier du dépôt,
   `daemon-reload`, redémarrage à froid. — **Prévention** : vérifier l'unité INSTALLÉE, pas
   celle du dépôt.

2. **`source` du formulaire d'import était avalé depuis le début**
   — **Symptôme** : la provenance d'un brouillon de livre restait vide. — **Cause** :
   `source: str = ""` à côté d'un `list[UploadFile]` est lu par FastAPI comme un paramètre de
   requête, pas comme un champ de formulaire ; le front l'envoyait bien en `FormData`.
   — **Solution** : `Form("")`.

3. **Le commit d'un brouillon écrivait hors transaction**
   — **Symptôme** : aucun à ce jour. — **Cause** : six écritures successives sur le pool ;
   un échec après le `DELETE FROM recipe_ingredient` laissait la recette présente et vide, et
   le brouillon encore `pending`. — **Solution** : `async with pool.acquire() as conn,
   conn.transaction():`, le patron que `ingest.py` appliquait déjà.

4. **Un `PATCH` sans clé `draft` écrasait le brouillon entier**
   — **Cause** : `data.get("draft") or data` suivi d'un `UPDATE` inconditionnel des trois
   colonnes. `{"title": "x"}` vidait ingrédients, étapes et slug. — **Solution** : fusion sur le
   brouillon stocké, et refus d'un titre vide.

5. **Une catégorie JSON-LD rendue en liste levait un 500**
   — **Symptôme** : `TypeError` sur `unicodedata.normalize(["Dessert"])`. — **Cause** :
   schema.org autorise une liste là où le code attendait une chaîne ; c'est la forme de
   Marmiton et d'AllRecipes. — **Solution** : `_first_text()` côté extraction, et
   `normalize_category` refuse un non-`str` au lieu de casser.

6. **`ALTER COLUMN ... USING` réécrivait la table `recipe` à chaque redémarrage**
   — **Cause** : avec un `USING`, PostgreSQL réécrit toujours, même quand le type est déjà bon.
   Cinq colonnes, donc cinq réécritures sous `ACCESS EXCLUSIVE` par `systemctl restart`.
   — **Solution** : garde sur `information_schema.columns`.

7. **`.git/index.lock` est resté deux fois, sans processus git vivant**
   — **Symptôme** : `fatal: Unable to create index.lock`. — **Cause** : dépôt sous Dropbox,
   verrou orphelin. — **Prévention** : vérifier `Get-Process git` AVANT de lever le verrou —
   un verrou tenu par un vrai processus ne se supprime pas.

8. **Le registre a failli perdre une relation** — la relation « doublon d'extraction JSON-LD
   avec deep-research » était portée par recipe-manager. Réécrire son entrée l'effaçait.
   Elle a été rattachée à CM2, qui porte désormais le code concerné.
