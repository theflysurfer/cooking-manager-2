## Achievements

### La dominance des cuissons, portée par le vocabulaire (SC-68)
- « Faites dorer », présent dans presque tout mijoté, déclenchait `pan-fried` avec le
  **même bonus (40)** que `stew` et faisait gagner *dorade* (150) sur *lotte* (135) en
  cocotte. Parade retenue : une table `dominates` dans
  `data/ontology/cooking-vocabulary.yaml` (v0.3.0), consommée par `drop_dominated()`
  avant tout scoring. `stew` et `slow-cooked` absorbent `pan-fried`, `pan-seared`,
  `stir-fry`.
- Vérifié **en production** sur `mafe-poulet`, qui contient « faire revenir les oignons »
  *et* « saisir les crevettes » : `/api/recipes/mafe-poulet/compatibility` rend
  `cooking_methods: ["stew"]` seul, et la règle ouest-africaine ancrée reste gagnante
  (cabillaud, confiance 1.0).
- La table ne porte **que le cas mesuré**. `oven` dominant `pan-seared` (saisir puis
  enfourner) est plausible et non observé — l'y inscrire serait le défaut reproché à
  `separate_dish`.

### `separate_dish` : le statut passe de note humaine à règle exécutée

### Recompte de `USE_CASES_TABLEE.md`

## Decisions
1. **La hiérarchie des cuissons vit dans le vocabulaire, pas dans le code** — **Choix** :
   champ `dominates` sur le concept, `drop_dominated()` le consomme — **Rationale** :
   une table de dominance écrite en Python serait invisible à `julien-audit-cooking-vault`
   et divergerait du YAML sans erreur ; le vocabulaire est déjà le foyer déclaré des
   cuissons — **Alternatives rejetées** : pondérer selon la position de l'étape (dépend de
   l'ordre de rédaction, fragile sur une fiche importée du web) ; dégrader le bonus des
   modes suivants (arbitraire — le « premier » dépend de l'ordre du vocabulaire).
2. **Le corpus web se scinde selon le dépôt propriétaire, il ne se déplace pas en bloc** —
   **Choix** : la mesure d'extraction chez recipe-manager, les défauts du moteur dans CM2 —
   **Rationale** : le handoff disait « rapatrier », mais le document portait aussi les deux
   défauts du moteur de substitutions, qui n'ont rien à faire chez le parseur —
   **Alternative rejetée** : déplacer le fichier entier.
3. **Pas de second magasin de brouillons côté CM2** — **Choix** : exposer `/parse-url` en
   proxy et ouvrir recipe-manager#5 pour la création de brouillon depuis une URL —
   **Rationale** : dupliquer `recipe_import_draft` pour un seul canal d'acquisition
   recréerait exactement le doublon d'extraction constaté entre deep-research#49 et
   `url_parser/` — **Alternative rejetée** : une table de brouillons locale à CM2.

## Problems
1. **`observed_in` s'arrêtait au YAML** — **Symptôme** : `accommodations_by_evidence()`
   trie par nombre d'observations ; sur l'artefact généré, `observed_in` était absent —
   **Cause** : le générateur `ontology-manager` a un jeu de champs fixe et ne propageait
   ni `observed_in` ni le nouveau `dominates` — **Conséquence évitée de justesse** : le
   tri aurait compté **zéro observation partout** et aurait paru fonctionner (l'ordre
   alphabétique de repli est plausible) — **Solution** : les deux champs propagés jusqu'au
   JSON, le chargement refuse une clé de `dominates` inconnue ou auto-citée —
   **Prévention** : un test vérifie que `observed_in` survit à la génération.
2. **`meal_attendance` n'a aucune écriture** — **Symptôme** : la hiérarchie de
   `attendees()` place l'override manuel au sommet, `load_referential_from_db()` va bien
   le chercher, et il n'arrive jamais — **Cause** : aucune route, aucun intent vocal,
   aucun code n'écrit dans cette table ; mesuré en prod, **0 ligne** — **Impact** : c'est
   la cause unique de 6 cas d'usage non couverts, dont toute la famille invités (les
   profils existent pourtant, 10 personnes en `extended_family`) — **Solution** : issue #73,
   pas de correctif dans cette session — **Prévention** : le résolveur répond correctement
   avec la trame, donc rien ne signale que sa couche prioritaire est morte. Famille « un
   signal absent lu comme un signal vert ».
3. **`stay.cooking` est exposé sans être consommé** — **Symptôme** : `/api/attendance`
   renvoie le drapeau, aucun calcul de courses ni de garde-manger ne le lit — **Impact** :
   un séjour à l'hôtel (`cooking=false`) génère quand même une liste de courses — cas F.31,
   F.32, F.34 — **Solution** : tracé dans #73.
4. **La cascade d'extraction ne descend pas — chiffré** — **Symptôme** : 34/34 extraites,
   **24/34 utilisables** — **Cause** : un tier est accepté dès que `ingredients` est non
   vide ; les 9 recettes de papillesetpupilles sortent en `jsonld` accepté avec 0 étape et
   0 quantité — **Preuve** : le tier `heuristic`, quand il est atteint, rend 2 à 7 étapes
   *et* les quantités — descendre aurait rattrapé les 10 — **Solution** : recipe-manager#4
   commentée avec un critère d'acceptation.
5. **Le gate commentaires sort rouge** — 615 constats sur 30 fichiers, dette préexistante
   répartie sur tout le dépôt (`nutrition.py` 59, `style.css` 57, `pantry.py` 54), non
   résorbée dans cette session. Déjà tracé : issue #71.

### Gotchas
- Deux variables `GITHUB_TOKEN` coexistent : celle du **processus** (un `gho_` périmé)
  masque celle de l'**utilisateur** (`ghp_`, valide). Poser
  `export GITHUB_TOKEN=$(powershell -NoProfile -Command '[Environment]::GetEnvironmentVariable("GITHUB_TOKEN","User")' | tr -d '\r')`
  avant tout `git push`/`gh`.
- Le générateur `ontology-manager` a un **jeu de champs fixe** : un champ ajouté au YAML
  n'atteint pas l'artefact tant que `cooking.py` ne le propage pas, et le consommateur lit
  alors une valeur vide sans erreur.
- Les URLs Marmiton redirigent : `recette_blanquette-de-veau-facile_18234` rend une
  « Fondue charolaise ». Ne pas en conclure que le parseur se trompe.
