## Objective
Exécuter le handoff de la session précédente : constituer le corpus qui débloque les trois
limites du moteur de substitutions relevées en prod (mijoté sans le mot, étape de garniture,
cuisine ouest-africaine). En creusant le gisement web, découvrir que deux dépôts avaient

## Decisions
1. **Cascade 3 tiers d'extraction : chez recipe-manager, pas deep-research** — **Choix** :
   recipe-manager garde l'extraction (modèle, `parse_ingredient()`, drafts), deep-research garde
   la découverte d'URLs (`recipe_web`) — **Rationale** : recipe-manager avait déjà une cascade
   plus complète (repli flaresolverr, 3 tiers) avant que deep-research n'en construise une
   seconde — **Alternative rejetée** : garder les deux implémentations en parallèle.
2. **Scinder `product-toolkit`, pas juste documenter la distinction** — **Choix** : nouveau repo
   `product-conception-toolkit` — **Rationale** : un `CLAUDE.md` qui assume les deux chaînes dans
   le même repo continuerait de s'ouvrir pour du branding et de rester invisible quand la doctrine
   de test dérive — exactement le mécanisme qui a produit le retard mesuré — **Alternative
   rejetée** : documenter sans scinder.
3. **`VOCABULARY.md` reste dans `product-toolkit`, jamais dupliqué** — **Choix** : le nouveau repo
   le référence en amont inter-dépôts — **Rationale** : `stakeholder`/`role` sont à la racine des
   deux chaînes, et une divergence entre deux copies serait pire que la confusion corrigée.

## Problems
1. **Édition directe de `repo-registry/data/projects.json`** — **Symptôme** : diff de 44 245
   lignes pour ~60 lignes de changement réel — **Cause** : `json.dump(..., indent=1)` a reformaté
   tout le fichier (original en `indent=2`), et surtout `projects.json` est un **artefact généré**
   par `discover.py`, jamais une source — l'avertissement est écrit en toutes lettres dans
   `relations.json` et dans le fichier lui-même — **Solution** : `git checkout -- projects.json`,
   édition refaite dans `relations.json`/`repo_skills.json`, régénération par `discover.py` —
   **Prévention** : skill `julien-ref-registry-edit` créée. Un commentaire dans un fichier ne se
   déclenche pas tout seul avant l'écriture ; une skill, si.
2. **Exposition d'un PAT en clair dans le transcript** — **Symptôme** : un message d'erreur
   PowerShell (binding de paramètre cassé par un alias `h`/`Get-History` shadowé) a affiché la
   valeur complète de deux variables `GITHUB_TOKEN` — **Cause** : je demandais l'affichage des 4
   premiers caractères de chaque token pour diagnostiquer une confusion entre deux variables du
   même nom (une `gho_` périmée héritée du processus, une `ghp_` valide posée en variable
   utilisateur) — **Solution** : signalé immédiatement à Julien, qui a choisi de ne pas révoquer
   ni purger le transcript — **Prévention** : ne jamais construire une commande PowerShell qui
   pourrait faire fuiter une valeur secrète dans un message d'erreur, même en cas d'échec de
   binding imprévu.
3. **Le catalogue `TEST_NOMENCLATURE.md` était en retard de deux documents** — voir § Scission.

### Gotchas
- Deux variables `GITHUB_TOKEN` coexistent dans l'environnement : celle du **processus** hérité
  (un vieux `gho_` périmé) masque celle de l'**utilisateur** (`ghp_`, valide) pour tout ce qui lit
  `os.environ`. `git` utilisait en plus une entrée périmée du Credential Manager Windows,
  indépendante des deux. Passer explicitement `$env:GITHUB_TOKEN=[Environment]::GetEnvironmentVariable(...,"User")`
  avant tout `git push`/`gh`.
- `repo-registry/data/projects.json`, `deployment_index.json`, `viewer/data.js` : **jamais** à la
  main, toujours via `discover.py` après édition des fichiers manuels — voir
  `julien-ref-registry-edit`.
