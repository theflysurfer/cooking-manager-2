## Decisions

1. **Le prompt vit dans le code, pas chez l'appelant**
   - **Choix** : corps du prompt versionné dans `recipe_manager/images.py` (`PROMPT_VERSION`).
   - **Rationale** : la cohérence du parc tient à ce qu'une recette ajoutée dans six mois
     produise une image de la même famille. Un prompt passé par l'appelant dérive au premier
     appel improvisé, et la grille photo-first se disloque.
   - **Alternative rejetée** : paramètre `prompt` dans la requête — souple, et c'est
     exactement la souplesse qui casse l'invariant.

2. **Reprendre la v1.1, surtout pas le prompt Waaker**
   - **Choix** : porter le prompt de CM2, pas celui du code Waaker exhumé.
   - **Rationale** : le prompt Waaker (« Professional food photography of… ») est *celui qui a
     échoué* : lu comme une commande de stylisme, il rendait table en bois, fenêtre et verre de
     vin — illisible à 360 px et différent à chaque génération.
   - **Alternative rejetée** : réutiliser l'existant Waaker par fidélité au legs.

3. **`MEDIA_ROOT` ne pointe pas vers le clone de CM2**
   - **Choix** : sortie dans `/opt/recipe-manager/media/recipes` ; les appelants qui veulent
     garder une image passent par `inline=true` et la committent chez eux.
   - **Rationale** : écrire dans le checkout d'un autre projet produit un fichier live-only,
     perdu au prochain rebuild et invisible en review (règle Code Mirroring).
   - **Alternative rejetée** : pointer directement chez CM2 — pratique, et silencieusement
     destructeur.

4. **`.jpg` tranche définitivement contre `.png`/`.webp`**
   - **Choix** : conversion systématique en JPEG côté endpoint.
   - **Rationale** : `ingest.py` ne scanne que `<slug>.jpg`. La note de passation Waaker disait
     `.png` et l'issue #54 disait `.webp` : les deux auraient produit des fichiers jamais
     rattachés à leur recette.

## Problems

1. **Une photo scrapée était une photo en sursis — 11 perdues en une ingestion**
   - **Symptôme** : après un `POST /api/ingest` de routine, 11 recettes se retrouvent sans
     photo, dont 9 au menu de la semaine. Aucune erreur, aucun warning.
   - **Cause** : `photo_url` est la seule colonne dont la valeur ne vient pas toujours du vault.
     Sans fichier local, elle est reconstruite à chaque ingestion par `_scrape_photo()`, qui
     dépend d'un site tiers joignable en 8 s — et l'upsert écrivait `photo_url=$24` **sans
     condition**, donc un fetch en échec remplaçait une photo existante par `NULL`.
   - **Solution** : `photo_url=COALESCE($24, recipe.photo_url)` (`00ed362`) + génération de
     fichiers locaux pour les 11 recettes concernées (`c94f128`), ce qui supprime la dépendance
     au réseau.
   - **Prévention** : consigné dans CLAUDE.md — un `photo_url` sans fichier local est en sursis ;
     la parade de fond est le fichier versionné, pas le scraping.

2. **Le prompt existe désormais à deux endroits**
   - **Symptôme** : `data/photo-prompt.md` (CM2) et `recipe_manager/images.py` portent tous deux
     la v1.1.
   - **Cause** : la doctrine était née côté CM2 ; l'implémentation vit côté recipe-manager.
   - **Solution** : l'implémentation est déclarée **faisant foi** dans les deux CLAUDE.md et en
     tête de `photo-prompt.md`, qui ne documente plus que le *pourquoi*.
   - **Prévention** : une divergence entre les deux ne se verrait qu'au moment où une image
     générée des mois plus tard cesserait de ressembler aux autres — d'où le pointeur explicite
     plutôt qu'une simple copie.

3. **`git pull` en root sur `/opt/recipe-manager` échoue en silence**
   - **Symptôme** : `sudo bash -c "cd /opt/recipe-manager && git pull …"` → `could not read
     Username for 'https://github.com'`, et la chaîne s'arrête avant la copie de l'unit.
   - **Cause** : le dépôt appartient à `automation` ; root ne voit pas ses credentials.
   - **Solution** : `git pull` **en tant qu'`automation`**, `sudo` réservé à `cp`/`daemon-reload`/
     `restart`.
   - **Prévention** : la sortie mêlée donnait l'illusion d'un succès — le contrôle qui a levé le
     doute est un `grep` du credential dans l'unit **installée** (rendu `0`), pas `is-active`.

### Gotchas

- **Générer une photo manquante** — ne jamais improviser de prompt :
  ```bash
  ssh srv759970 'curl -s -X POST "localhost:8796/recipes/<slug>/generate-image?inline=true"' \
    | python -c "import json,sys,base64; d=json.load(sys.stdin); open('web/media/recipes/'+d['slug']+'.jpg','wb').write(base64.b64decode(d['image_base64']))"
  ```
  puis **committer** : le fichier écrit par l'endpoint vit sur la box et n'est pas versionné.
- **Un `photo_url` sans fichier local est en sursis** — il se reconstruit à chaque ingestion
  depuis un site tiers. Le `COALESCE` empêche l'effacement, il ne crée pas la photo.
- **`/opt/recipe-manager` se pull en `automation`**, jamais en root (credentials HTTPS).
- **Gemini rend un 200 sans image** quand la sécurité bloque — `_extract_image()` lève plutôt
  que de renvoyer un succès vide.
