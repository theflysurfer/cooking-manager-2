## Objective
Migrer le garde-manger de Markdown vers PostgreSQL (Phase 1 du plan de migration) et créer un serveur MCP pour que les LLM puissent interagir avec le garde-manger, les recettes et les menus.

## Achievements
- **Table `pantry_item` créée** : 17 colonnes, contrainte UNIQUE `(name_normalized, section)`, 3 index. La DB devient source de vérité (pas le vault, qui n'est qu'une source d'ingestion).
- **Ingestion vault → DB** : `_ingest_pantry()` dans `backend/ingest.py` — parse `Garde-manger.md`, upsert chaque item avec `source='vault'`, supprime les items vault absents du Markdown (les items API/MCP/voix sont préservés). 256 items parsés, 249 uniques après déduplication.
- **API `GET /api/pantry` migrée** : lit désormais depuis `pantry_item` (plus le Markdown). Enrichi : `id`, `name_normalized`, `qty_value`, `unit`, `perishable`, `source`, `notes` par item. Staleness calculée depuis `MAX(updated_at)`.
- **Endpoints CRUD ajoutés** : `POST /api/pantry/items` (création + auto-normalisation + détection périssable), `GET /api/pantry/items/{id}`, `PUT /api/pantry/items/{id}` (update partiel), `DELETE /api/pantry/items/{id}`, `GET /api/pantry/search?q=` (ILIKE). Tous vérifiés sur le VPS.
- **Fix parser** : `parse_pantry()` ne stripait pas les annotations `(entré ...)`, `# status=...`, `(constaté ...)` quand la ligne n'avait pas de séparateur `—` → noms pollués en DB. Corrigé par 3 regex de nettoyage.
- **Serveur MCP créé** : `backend/cooking_mcp.py` — 10 outils (`pantry_list`, `pantry_search`, `pantry_add`, `pantry_update`, `pantry_remove`, `shopping_list`, `recipe_search`, `recipe_detail`, `menu_current`, `pantry_ingest`). Transport stdio, appelle l'API HTTP du VPS.
- **MCP enregistré localement** : `.claude/settings.local.json` pour ce projet.
- **Issues #36 et #37 fermées** (migration DB + API CRUD).
- **Issue #46 créée** : enregistrement MCP dans le proxy gateway global.

## Decisions
1. **DB = source de vérité pour le garde-manger**
   - **Choix** : contrairement aux recettes et menus (vault = source), le garde-manger a la DB comme source de vérité. Le vault n'est qu'une source d'ingestion parmi d'autres.
   - **Rationale** : le garde-manger est modifié par API, voix et Auchan — pas seulement par le vault. La DB est la seule surface partagée.
   - **Alternative rejetée** : garder le Markdown comme source → impossible de gérer les items ajoutés par voix/API sans réécrire le fichier.

2. **Upsert sur `(name_normalized, section)`**
   - **Choix** : un produit est unique par rayon. La ré-ingestion met à jour les existants, pas de doublon.
   - **Rationale** : le même produit peut exister dans deux rayons (ex. "huile d'olive" en Sec et en Condiments) mais pas deux fois dans le même rayon.

3. **MCP appelle l'API HTTP, pas la DB directement**
   - **Choix** : le MCP est un client HTTP du VPS, pas un accès direct à PostgreSQL.
   - **Rationale** : pas besoin de credentials DB locaux, la logique métier reste centralisée dans l'API.

## Problems
1. **Noms d'items pollués par les annotations**
   - **Symptôme** : items en DB comme "Aceto Balsamico di Modena Douceur Auchan (entré 2026-07-07) # status=ok"
   - **Cause** : `parse_pantry()` ne nettoyait les annotations que quand la ligne contenait un `—`. Sans séparateur, toute la ligne devenait le nom.
   - **Solution** : 3 regex de nettoyage dans `cooking_manager/pantry.py` (`# status=...`, `(entré ...)`, `(constaté ...)`).
   - **Prévention** : le test unitaire `test_parse_pantry_annotations` couvre ce cas.

2. **Premier déploiement sans commit**
   - **Symptôme** : `git pull` sur le VPS → "Already up to date"
   - **Cause** : le code n'avait pas été committé/poussé avant le déploiement.
   - **Solution** : committer et pousser d'abord, puis déployer.
