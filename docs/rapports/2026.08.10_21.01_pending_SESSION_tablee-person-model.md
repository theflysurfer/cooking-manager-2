## Objective

Concevoir le modèle de données pour la « tablée » : cartographier
exhaustivement les types de personnes qui peuvent s'asseoir à table
(foyer, famille élargie, amis, occasionnels), puis créer les tables
PostgreSQL correspondantes.

## Achievements

- **Taxonomie des protagonistes** — 4 cercles identifiés (foyer,
  famille élargie, amis proches, occasionnels) avec 7 rôles dans le
  foyer (adulte, enfant, nouveau conjoint, enfant du conjoint,
  demi-frère, ascendant hébergé, caregiver).
- **Recherche concurrentielle** — aucune app grand public ne croise
  présence variable + profil diététique. MealSuite/Kafoodle (hôpital)
  ont le modèle le plus riche (3 niveaux de sévérité = exactement ce
  que CM2 fait déjà). Mealie a la hiérarchie Group > Household > User
  mais zéro profil diététique.
- **8 tables créées dans `backend/db.py`** :
  - `person` — registre universel (remplace `convive`)
  - `relationship` — parent/enfant, conjoint, fratrie
  - `household` + `household_member` — foyers
  - `person_group` + `person_group_member` — raccourcis nommés
  - `custody_schedule` — garde alternée par enfant
  - `canteen_schedule` — cantine par enfant et par jour
  - `meal_attendance` — tablée effective par repas
- **Migration convive → person** — les données existantes de la table
  `convive` sont copiées vers `person` avec extraction du diet/dislikes/
  forbidden depuis le `TEXT[]` de contraintes. Foyer principal auto-créé.
- **Tests et lint** — 114 passed, 23 skipped, ruff clean.

## Decisions

1. **Registre universel `person`**
   - **Choix** : une seule table pour tous les cercles, avec un champ
     `circle` (household/extended_family/friend/occasional)
   - **Rationale** : Philippe est à la fois « grand-père » et « convive
     semi-végétarien » ; deux tables = jointure obligatoire partout
   - **Alternative rejetée** : tables séparées par cercle → complexité
     de requêtage

2. **Relations typées plutôt qu'arbre généalogique**
   - **Choix** : 3 types de relation (`parent_of`, `partner`, `sibling`)
     stockés dans un seul sens, l'inverse se déduit
   - **Rationale** : suffisant pour résoudre « les enfants de Paul »,
     « ses parents », « sa femme ». Grand-parent = composition
     (parent du parent)
   - **Alternative rejetée** : types spécifiques (grandparent_of,
     uncle_of) → explosion combinatoire sans gain

3. **Garde alternée par personne, pas globale**
   - **Choix** : `custody_schedule` avec une ligne par enfant, chacun
     ayant son propre rythme et sa date de référence
   - **Rationale** : couvre la garde croisée (enfants du conjoint
     viennent les semaines inverses)

4. **Table `convive` conservée**
   - **Choix** : rétrocompatibilité, pas de migration destructive
   - **Rationale** : le code existant (`app.py::menu_compatibility`,
     `ingest.py`) continue de fonctionner tel quel pendant la transition

## Critical Review

> Cette section est destinée à être relue avec un œil neuf, détaché de
> l'élan de la session.

### Ce qui a été fait (résumé neutre)

- 8 tables PostgreSQL ajoutées au schéma pour modéliser qui mange à
  quel repas, avec des profils alimentaires et des relations familiales
- Une migration SQL copie les données existantes de `convive` vers
  `person`
- Aucun code applicatif n'a été modifié — les tables sont posées mais
  pas encore utilisées

### Hypothèses non vérifiées

- [ ] La migration SQL `INSERT INTO person ... SELECT FROM convive`
  gère-t-elle correctement un convive sans aucune contrainte (constraints
  = '{}') ? Le `COALESCE` sur le `SELECT unnest` avec un array vide
  pourrait ne rien retourner
- [ ] Le `UNIQUE(name, circle)` permet deux « Philippe » (un en
  `household`, un en `extended_family`) — est-ce voulu ou un bug ? Dans
  la vraie vie, Philippe le grand-père et Philippe le voisin sont deux
  personnes, mais la contrainte ne suffit pas si deux amis portent le
  même prénom
- [ ] `meal_attendance` n'a **aucune contrainte d'unicité** — rien
  n'empêche d'insérer deux fois la même personne au même repas
- [ ] Les CHECK sur `slot` dans `meal_attendance` sont-ils cohérents
  avec ceux utilisés dans `menu_meal.slot` (qui n'a PAS de CHECK) ?
- [ ] La migration `INSERT INTO household_member` rattache toute
  `person` avec `circle='household' AND default_attendance='always'` —
  mais les enfants en garde alternée ont `default_attendance='scheduled'`,
  donc ils ne seraient PAS rattachés au foyer

### Régressions potentielles à tester

- [ ] `init_schema()` exécute SCHEMA_SQL puis MIGRATIONS_SQL — la
  migration `INSERT INTO person SELECT FROM convive` s'exécute à
  **chaque démarrage** du serveur. Le `ON CONFLICT DO NOTHING` protège-
  t-il vraiment ? (La contrainte unique est `(name, circle)`, pas `(name)`)
- [ ] La migration crée le foyer avec `WHERE NOT EXISTS (SELECT 1 FROM
  household WHERE is_primary)` — mais rien n'empêche de créer un second
  foyer `is_primary=TRUE` après coup (pas de contrainte unique partielle)
- [ ] `custody_schedule.reference_date` est `NOT NULL` — la migration
  convive → person ne crée PAS de custody_schedule, donc `attendees()`
  futur devra gérer le cas « enfant sans schedule »

### Ce qui n'a pas été testé

- [ ] Exécution réelle de la migration SQL sur la DB du VPS (qui a des
  données vivantes dans `convive`)
- [ ] Comportement de `unnest('{}'::text[])` dans le `SELECT` de la
  migration (array vide)
- [ ] Performance des requêtes avec jointures person → relationship →
  person (pour « les enfants de Paul »)

### Questions ouvertes pour le relecteur

1. Faut-il un index unique partiel `CREATE UNIQUE INDEX ON household
   (is_primary) WHERE is_primary` pour garantir qu'il n'y a qu'un seul
   foyer principal ?
2. `meal_attendance` devrait-elle avoir un `UNIQUE(menu_id, day, slot,
   person_id)` pour éviter les doublons ?
3. Le champ `role` de `person` (adult/child/caregiver) et le champ
   `role` de `household_member` (resident/regular_guest) portent le même
   nom pour des choses différentes — source de confusion ?
4. La contrainte `person.name` n'est pas `UNIQUE` globalement (seulement
   `UNIQUE(name, circle)`) — deux amis « Marie » dans le cercle `friend`
   seraient en conflit. Faut-il `UNIQUE(name, full_name)` à la place ?
