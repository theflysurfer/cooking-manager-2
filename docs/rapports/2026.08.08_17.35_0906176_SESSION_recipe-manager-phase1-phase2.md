## Decisions
1. **Base de données unique, pas de schémas PG séparés**
   - **Choix** : les trois apps (CM2, recipe-manager, Waaker) partagent `cooking_manager` dans postgresql-shared
   - **Rationale** : même VPS, FK croisées directes, pas de complexité inter-schéma
   - **Alternative rejetée** : schémas PG séparés (overhead d'administration pour un gain d'isolation inutile sur un mono-VPS)

2. **CM2 colocataire (accès DB direct), pas client HTTP**
   - **Choix** : CM2 garde ses requêtes asyncpg sur les tables recettes
   - **Rationale** : même VPS, même DB, zéro latence réseau, pas de dépendance runtime à recipe-manager pour les lectures
   - **Alternative rejetée** : CM2 appelle recipe-manager via HTTP (ajouterait de la latence et un point de défaillance pour un service colocalisé)

3. **`cooking_manager/` conservé dans CM2**
   - **Choix** : vault.py, normalizer.py, ingredients.py restent dans CM2
   - **Rationale** : trop de consommateurs locaux (pantry.py → normalize_name + UNIT_ALIASES, ingest.py → read_menus/read_convives, build.py → tout). Retirer ces fichiers casserait menus, convives, pantry, legacy build
   - **Alternative rejetée** : supprimer et importer depuis recipe-manager (impliquerait pip-install de recipe-manager comme dépendance, prématuré)

## Problems
1. **Ruff line-length à 88 par défaut dans recipe-manager**
   - **Symptôme** : 17 erreurs E501 au premier lint
   - **Cause** : `line-length` non déclaré, défaut ruff = 88, code extrait de CM2 qui utilise 120
   - **Solution** : `line-length = 120` dans `pyproject.toml`
   - **Prévention** : toujours configurer `line-length` explicitement dans un nouveau pyproject.toml

### Questions ouvertes pour le relecteur
1. **`Wants=` vs `Requires=`** : le service unit de CM2 utilise `Wants=recipe-manager.service`. Si recipe-manager ne démarre pas (crash, venv cassé), CM2 démarrera quand même et échouera sur `CREATE TABLE menu_meal` (FK vers `recipe`). Faut-il passer à `Requires=` ?
2. **Double ingestion** : CM2 et recipe-manager ont chacun un endpoint `/ingest` qui écrit dans les mêmes tables. En production, lequel utilise-t-on ? Le dual-write est-il un risque de conflit ou de données incohérentes ?
3. **Code dupliqué** : `vault.py`, `normalizer.py`, `ingredients.py` existent dans les deux repos. Quand un bug est corrigé dans l'un, il faut le corriger dans l'autre. Faut-il faire de recipe-manager un package pip installable par CM2 pour éliminer la duplication ?
4. **`Environment=DATABASE_URL=...` dans le service unit de recipe-manager** : le DSN avec mot de passe est en clair dans le fichier unit (644). Faut-il migrer vers credstore (comme CM2 avec `run-with-cred.sh`) ?

### Alternatives non explorées
- **recipe-manager comme package Python** : au lieu d'un service HTTP séparé, recipe-manager aurait pu être un package pip que CM2 et Waaker importent. Avantage : pas de service à déployer, pas de dual-write. Inconvénient : Waaker est en JS → il ne peut pas importer un package Python, d'où le choix d'une API HTTP.
- **Monorepo** : garder le code recettes dans CM2 et exposer l'API depuis CM2 directement (sous `/api/recipes/shared`). Avantage : pas de duplication. Inconvénient : Waaker dépendrait de CM2 (couplage fort), et le modèle de recettes resterait une sous-partie de CM2 au lieu d'être un service autonome.
