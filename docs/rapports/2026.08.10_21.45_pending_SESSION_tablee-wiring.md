## Objective

Câbler les 8 tables tablée (créées à la session précédente) dans le code
applicatif : review du schéma, écriture dans `person` à l'ingestion,
refactoring de `presence.py` en data-driven, API CRUD complète, et endpoint
de seed des données familiales.

## Achievements

- **Review du schéma tablée** — 4 corrections appliquées :
  - Renommage `household_member.role` → `membership` (évite la confusion
    avec `person.role`)
  - Index unique partiel `idx_household_one_primary` pour garantir un
    seul foyer principal
  - Index unique partiel `idx_meal_attendance_unique` pour empêcher les
    doublons de personne par repas
  - Migration `INSERT INTO household_member` corrigée : filtre sur
    `circle = 'household'` au lieu de `default_attendance = 'always'`
    (les enfants en garde alternée n'étaient pas rattachés au foyer)
- **Person câblée dans l'ingestion** — `ingest.py` écrit désormais dans
  `person` en parallèle de `convive` (dual-write), avec mapping
  `circle`/`default_attendance` dérivé de `is_guest`
- **`presence.py` refactoré en data-driven** — 3 dataclasses ajoutées
  (`HouseholdConfig`, `CustodyInfo`, `CanteenEntry`) ; `attendees()` et
  `week_grid()` acceptent un paramètre `household` optionnel ; les
  constantes historiques restent en fallback (100 % rétrocompatible)
- **API CRUD complète** — endpoints REST pour `person`, `household`,
  `relationship`, `custody_schedule`, `canteen_schedule` (list, create,
  update, delete)
- **Endpoint `POST /api/seed`** — peuple les 4 membres du foyer (Julien,
  Clémence, Léa, Titouan), 6 relations, les schedules de garde alternée
  et de cantine
- **`load_household_config()`** — fonction qui construit un
  `HouseholdConfig` depuis la DB, câblée dans
  `/api/menus/{slug}/compatibility`
- **Gates verts** — ruff clean, pyright 0 errors, 114 tests passed,
  iOS 12 gate 100/100

## Decisions

1. **Dual-write convive + person**
   - **Choix** : écrire dans les deux tables à l'ingestion
   - **Rationale** : rétrocompatibilité totale — le code existant
     (`menu_compatibility`) continue de lire `convive` pendant la
     transition
   - **Alternative rejetée** : remplacer d'emblée `convive` → casse le
     code en production

2. **`presence.py` reste pur (pas d'I/O)**
   - **Choix** : `HouseholdConfig` est construit dans `app.py`
     (`load_household_config`) et passé en paramètre
   - **Rationale** : respecte la frontière architecturale
     (`cooking_manager/` = domaine pur, `backend/` = I/O)

3. **`reference_present` sur `CustodyInfo`**
   - **Choix** : booléen qui permet d'inverser le pattern de garde
   - **Rationale** : couvre la garde croisée (enfants du conjoint
     présents les semaines inverses) sans multiplier les patterns

## Problems

1. **Forward reference `HouseholdConfig` dans `app.py`**
   - **Symptome** : ruff F821 `Undefined name 'HouseholdConfig'`
   - **Cause** : l'import était à l'intérieur du corps de
     `load_household_config`, rendant l'annotation de retour
     `"HouseholdConfig"` non résolvable
   - **Solution** : import remonté au top-level de `app.py`
   - **Prevention** : toujours importer au top-level les types utilisés
     dans les annotations

### Gotchas

- `POST /api/seed` est idempotent (`ON CONFLICT DO NOTHING`) — peut être
  relancé sans risque
- Les constantes `ADULTS`/`CHILDREN`/`CUSTODY_REFERENCE_WEEK` restent en
  fallback — un appel à `attendees()` sans `household` fonctionne comme
  avant
- Deux sources de vérité coexistent (`convive` et `person`) — la
  migration destructive de `convive` est reportée
- `load_household_config()` ne charge que les personnes
  `circle='household'` et `is_active=TRUE` — les invités ponctuels ne
  sont pas dans le `HouseholdConfig`
